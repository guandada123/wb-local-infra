# GUI 自动化闸门：点之前先看屏幕上是什么

> 建立于 2026-11-24，起因是当天**差点把 274GB 数据抹掉**。脚本 `bin/wb-ui-guard.py`。

## 一、起因（不写清楚就会被人删掉）

那天要给时间机器加一块盘。因为 `tmutil setdestination` 在 macOS 26 上被 TCC 挡住（root 也不行），
于是改用界面操作——**用坐标点击在系统设置里连点了七八次**。

中途弹出一个对话框：要求**抹掉 ZHITAI** 才能用作备份磁盘。那是删掉全部数据的按钮。
当时是按 Esc 救回来的。

所以结论不是「下次小心点」，而是：**没出事靠的是临场反应，不是设计**。
同一天还有两处同类问题——恢复密钥出现在屏幕上被截屏读到；让用户执行 `pbpaste > key文件`，
结果命令自身覆盖了剪贴板，文件里存的是一条命令。

## 二、三道判据

| id | 判据 | 触发条件 | 动作 |
|---|---|---|---|
| D1 | 前台应用禁令 | 前台是 系统设置 / 磁盘工具 / 密码(钥匙串) / SecurityAgent / 安装器，**按名字或 bundle id 任一命中** | 拒绝执行坐标点击，**不按键** |
| D2 | 危险关键词 | 模态框文本含 抹掉 / 抹除 / 格式化 / 初始化 / 删除卷 / erase / wipe / format… | **先按 Esc**，再拒绝 |
| D3 | 机密关键词 | 模态框文本含 恢复密钥 / recovery key（**只认这个**，见下） | 拒绝，**绝不按 Esc** |
| — | fail-closed | 模态框存在但看不懂 / 屏幕读不到 / AX 超时 | 一律拒绝 |

两条容易写错的细节：

- **D2 与 D3 的动作相反。** 危险对话框要 Esc 取消；机密对话框按 Esc 会把密钥的唯一一次显示关掉，
  等于把用户的救命钥匙丢掉。这两件事共用一个「拦截」分支是错的。
- **D3 的匹配必须窄。** 曾写成 `("恢复密钥", "密钥")`，而"密钥"会把钥匙串口令框、SSH 口令提示
  一并判成机密态 → 一律停手等人工（2026-11-24 审计 P2-2）。D3 存在的唯一理由是 Esc 会毁掉
  **恢复密钥**的唯一一次显示；别的"密钥"字眼没有这个性质。现已收窄，并加了一条对偶用例守着。
- **英文词按词边界匹配**（`\bformat\b`），否则 `formatted` 会误命中，把正常流程打断；
  中文按子串（中文没有词边界问题）。
- **D1 不能只认应用名**。macOS 26 把「钥匙串访问」改名为「密码」，进程名变成 `Passwords`，
  名字表整条失效 —— 2026-11-24 实弹测试时，前台就是 `Passwords`，`cliclick p` 照样放行（rc=0）。
  修法：名字与 **bundle id** 双轨，任一命中即拒；bundle id 由 App 自身声明，改名/升级不变。
- **前台是谁必须在同一条命令里判定完**。每条 shell 命令都会把 WorkBuddy 抢回前台，
  所以「先开 A 应用、再单独跑一次 cliclick」测出来的永远是 WorkBuddy —— 会得到假放行。

## 二·五、扫描范围：为什么不是「只看前台」

第一版只扫前台应用的窗口。实弹测试发现这是**错的模型**：

> 屏幕上两个对话框浮在最上面，闸门却报「0 个模态」——因为它们的属主是**后台**的
> System Events（`visible = false`），而坐标点击命中的是「屏幕最上层的窗口」，与「谁在前台」无关。

修的过程里有三次量化取舍：

| 方案 | 实测代价 | 结论 |
|---|---|---|
| 只扫前台 | ~0.1s | 漏掉浮层对话框（就是它骗过了自检） |
| 遍历全部 87 个进程 | **7.9s** | 每次点击等 8 秒，不可接受 |
| 前台 + 白名单属主，且先取全部进程名 | **1.6s** | 采用 |

中间还踩了一个：直接 `byName` 查不存在的进程，每个要卡好几秒，7 次查询把总耗时推到 **11s**。
必须先调一次 `se.processes.name()` 拿到全部名字，只对确实存在的属主发查询。

**刻意排除 NotificationCenter。** 它的「对话框」是通知：实测无任何可点按钮、Esc 关不掉。
把它算成阻塞项后，一条「App 后台活动」通知让所有点击永久 `rc=6` —— 闸门变成死锁。
通知不挡坐标点击的落点，所以不参与判定。

## 三、为什么它必须接线

PATH 实测顺序：`/opt/homebrew/bin`(第 13 位) 在 `~/.local/bin`(第 28 位) **之前**。
也就是说在 `~/.local/bin` 放同名脚本挡不住 `cliclick`；真能拦住的只有一个位置：

```
/opt/homebrew/bin/cliclick   ← 一条指向 Cellar 的软链（5.1）
```

`install-interlock` 把它换成 4 行 shim：先过闸门，再转发真身。原目标路径记在
`~/.local/etc/wb-ui-guard.json`，`remove-interlock` 一键还原。目录属 `guan:admin`，**不需要 sudo**。

接线后的自检**不能只看有没有输出**：`cliclick` 无参数时打的是
「You did not pass any commands…」（不含 `Usage` 字样），早期版本按 `Usage` 匹配会误判失败并自动回滚。
现在用 `cliclick p`（打印鼠标坐标）验证「真的转发到了真身」。

## 四、自身位断言

```bash
wb-ui-guard.py status      # rc=0 才算接线；rc=7 表示没接
```

它回答三件事：闸门文件在哪、`interlock: 已接线/未接线`、`PATH 解析` 指向谁。
没有这一条，闸门就只是「仓库里的一个文件」，和一段注释没有区别。

## 五、已知边界（诚实清单）

1. **只管 `cliclick`**。直接 `osascript -e '... click at {x,y}'`、或 AppleScript 的 `AXPress`
   不走这道闸门。它不是沙箱。
   - 同源的第二个缺口：**D1 判的是「前台应用」，而坐标点击命中的是「最上层的窗口」**。
     后台开着的系统设置若正好压在点击点上，闸门看不见。要闭合它必须先拿到窗口 z 序，
     2026-11-24 试过三条路都没成：
     · `pyobjc`：`/usr/bin/python3` 与 `~/.workbuddy/binaries` 的 3.13.12 **都没有 Quartz 模块**
     · JXA ObjC bridge：`ObjC.import('CoreGraphics'|'Cocoa')` 后 `CGWindowListCopyWindowInfo`
       返回的对象不可解（`count=0` / `deepUnwrap` 得 `len=undefined`）
     · 退路「用 AX 窗口矩形判断点是否落在受禁窗口内」会**过度拒绝**：系统设置窗口 723×959
       常开着，盖住半个屏幕，做了之后大部分点击都会被拒 —— 等于把工具废掉
     所以选择**不做**，并在这里写明：要用时先关掉系统设置/磁盘工具。
     若将来装了 pyobjc，正确做法是取 z 序里最上层窗口的 owner，再判是否受禁。
2. **只认前台应用与原生模态框**。网页里的 confirm 框不在 AX 树里，D1 只能靠前台应用兜。
3. **实弹测试：D1、D2 已过，D3 未过**（2026-11-24）
   - D1 ✅ 前台 `Passwords` → `cliclick p` 被拒 `rc=3`、无坐标输出、日志留痕；退出后恢复 `rc=0`
   - D2 ✅ 自造假对话框（文字含「抹掉 ZHITAI 上的所有数据」，不含任何危险操作）→
     `rc=2`、自动按 Esc 把框关掉、日志留痕 `BLOCK ... hits=['抹掉'] 已按 Esc`
   - D3 ❌ **未做实弹**。需要屏幕上真出现「恢复密钥」，那只有开 FileVault 才有，
     而用户已决定不开。D3 只靠 13 项故障注入 + 4 次变异测试反证。
   - 真实的「抹掉磁盘」系统对话框**始终刻意不制造**，不拿真盘试。
4. **造测试对话框会留下僵尸窗口**。`pkill` 掉弹框进程后，窗口仍留在屏幕上，
   而 Esc 到不了（属主已死）—— 只能 `killall "System Events"`（它会自动重启）才清掉。
   教训：测完要主动关框，不要指望杀进程。
5. **`brew upgrade cliclick` 会覆盖 shim**，状态退回「未接线」；`status` 会报 rc=7，重跑
   `install-interlock` 即可。这是设计上的可发现降级，不是静默失效。
6. **自检不写真实日志**。否则 `status` 的「历史拦截 N 次」会混进自检噪音，变成自己会涨的假计数。

## 六、维护

```bash
python3 bin/wb-ui-guard.py self-test        # 13 项，每项只注入一个条件
python3 bin/wb-ui-guard.py scan             # 只判定，不动屏幕（排障第一步）
python3 bin/wb-ui-guard.py install-interlock   # 接线
python3 bin/wb-ui-guard.py remove-interlock    # 还原 brew 软链
```

改词表就改 `bin/wb-ui-guard.py` 顶部的 `DENY_APPS` / `BLOCK_CN` / `BLOCK_EN` / `SECRET_CN` / `SECRET_EN`。

变异测试（改完判据必须做，否则不知道用例有没有强度）：

- 把「抹掉」从 `BLOCK_CN` 删掉 → `抹掉 ZHITAI 确认框` 那一项必须变红
- 让机密分支也调 `press_escape()` → `恢复密钥（不许按 Esc）` 那一项必须变红
- 去掉 bundle 判据、只留名字 → `只靠 bundle 命中` 那一项必须变红
- 把 `SECRET_CN` 改回 `("恢复密钥", "密钥")` → `普通密钥提示不算机密态` 那一项必须变红

四条都实测过：各让自检从 13/13 掉到 12/13，且**只有那一项**红。

### 成本（实测，2026-11-24）

| 场景 | 单次 cliclick 调用额外耗时 |
|---|---|
| 屏幕上无模态 | **0.32 秒** |
| 有模态需遍历文本 | **1.6 秒** |

全机只有闸门自己调用 `cliclick`（`grep -rl` 仅此一处 + 一篇旧记忆），所以这点开销实际由我承担，
不影响任何既有自动化。

### 回滚路径有测试了

`cmd_install` 在自检失败时会自动还原软链。这条路径此前零测试（审计 P3-3），现由
`TestInterlockRollback` 覆盖：注入失败 → 断言 rc=1 且 INTERLOCK 恢复为软链；
注入成功 → 断言 INTERLOCK 变成 shim 且内容含 `wb-ui-guard`。

拦截记录：`~/.local/log/wb-ui-guard.log`（内盘；写外置卷会 TCC EPERM）。

**改完必须 `./install.sh --apply` 再测。** 实测踩过：改的是仓内 `bin/wb-ui-guard.py`，
而 `cliclick` 走的是 `~/.local/bin` 的副本 —— 于是出现「`scan` 判定 BLOCK，`cliclick` 照样放行」
的矛盾。这正是 `test_no_drift` 存在的理由。
